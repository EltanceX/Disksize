# 快照内文件夹局部重扫：方案与实现步骤

日期：2026-11-18。

状态：步骤 1 至 6 已完成。schema 为 5，局部重扫入口、原子合并、恢复和界面已通过回归、真实强杀/ENOSPC、百万节点规模和日常 UI 验收。关闭两个测试开关且 native -O2 的普通 Profile 已覆盖安装，原有 8 份快照完整保留。最终数据、包指纹及查询尾延迟边界见[正确性、性能与交付验收](./snapshot-subtree-rescan-acceptance.md)。步骤 1–5 的历史记录分别见[契约](./snapshot-subtree-rescan-contract.md)、[持久任务](./snapshot-subtree-rescan-persistence.md)、[合并](./snapshot-subtree-rescan-merge.md)、[服务](./snapshot-subtree-rescan-service.md)和[界面](./snapshot-subtree-rescan-ui.md)。

## 1. 目标与推荐方案

在已有快照中选中文件夹，手动重新扫描该目录及其后代，成功后更新同一份快照的数据。

推荐采用“暂存扫描结果 -> 校验 -> 事务内替换和汇总 -> 发布新 revision”的流程：

- 保留快照 ID 和对应 session ID，不自动增加一份完整快照。
- 文件系统遍历只覆盖选中子树，不重新遍历整个快照根目录。
- 扫描阶段继续提供旧结果；提交前失败或取消不改变已有快照。
- 成功提交后，旧子树被替换，不自动保存可撤销的完整旧版本。
- 只读取扫描目标的文件元数据，不修改、删除或复制目标文件内容。
- 第一版只接受完整成功的子树结果；Partial 合并、批量目录刷新和自动刷新暂不实现。

为保证正确性，第一版允许在数据库内重新计算该快照的全部硬链接归属和目录汇总。局部扫描不等于所有数据库工作都局部化；后续根据测量结果再做增量汇总优化。

## 2. 现有实现与需要调整的约束

| 现有实现 | 对局部重扫的影响 |
| --- | --- |
| [IndexStore](../android/app/src/main/kotlin/com/example/disksize/index/IndexStore.kt) 原有 schema 4，步骤 2 增量升级到 5；快照引用最终 session、revision 和容量 | 不必复制整份快照，但提交时必须同步更新 session 与 snapshot 的 revision、容量和完整性 |
| `IndexStore.finalize()` 明确拒绝重复处理已生成快照的 session | 新增专用局部更新入口；不能移除保护后直接重复调用现有 finalize |
| 导入节点 ID 从本次扫描的根开始，父节点、路径和深度按扫描根生成 | 暂存结果合并时必须重新映射，不能直接搬入已有 session |
| 硬链接按 device/inode 分组，以最小原始相对路径确定容量归属 | 子树变化可能影响树外节点及其祖先的统计 |
| [IndexQueries](../android/app/src/main/kotlin/com/example/disksize/index/IndexQueries.kt) 的游标绑定 revision | 更新后必须拒绝旧游标，界面重新查询 |
| [SnapshotQueries](../android/app/src/main/kotlin/com/example/disksize/index/SnapshotQueries.kt) 校验快照 revision，并维护分批生成的对比缓存 | 同步失效磁盘缓存和内存中的构建器，避免混合不同版本 |
| [目录页](../lib/features/explorer/explorer_page.dart) 的“刷新索引”只重新读取数据库 | 保留重新加载能力，与新“重新扫描此文件夹”明确区分 |
| 当前元数据传输协议为 v4，Root 只负责扫描和传输，普通 UID 负责索引 | 复用当前优化链路，不回退旧协议或把数据库处理移到 Root |

历史快照的不可变约定见[阶段 8](./phase8-snapshots.md)。本方案为显式授权的局部更新增加例外，不允许普通查询、重新加载或重复 finalize 隐式修改历史结果。

## 3. 产品行为

### 3.1 入口与范围

- 在目录列表的操作菜单、树图选中目录和目录详情中提供“重新扫描此文件夹”。
- 默认包含全部后代，不提供容易产生歧义的“仅当前层”模式。
- 首次操作显示目标路径，并确认将更新当前快照；名称和异常字节沿用现有转义显示。
- 保持原扫描后端，不允许把 Root 快照的局部结果降级为普通权限扫描后直接合并。
- 普通文件和符号链接不提供此目录操作；选中快照根目录时，范围即整个快照，但仍更新原快照。
- “已保留”快照建议同时禁止局部更新，提示先取消保留。原保留标记目前仅保护删除，这一规则属于本功能新增行为。

### 3.2 进度与结果

- 显示扫描、校验、应用更新等阶段，以及已发现条目数；未知总量时不用伪造百分比。
- 提交前允许取消；取消后保留旧结果。提交已成功时返回完成状态，不再显示“取消成功”。
- 扫描期间可浏览旧 revision；应用更新期间不得展示一半新、一半旧的统计。
- 成功后刷新目录、大文件、详情、树图、快照列表和对比相关数据。
- 优先保留选中目录与排序设置；旧子节点 ID 失效时，按原始相对路径重新定位，找不到则回到最近仍存在的祖先。
- 分页游标全部重新获取，不能沿用旧页码对应的旧游标。

### 3.3 时间与历史语义

- 保留原始扫描起止时间和快照创建时间，不把它们改成此次局部扫描时间。
- 增加最近局部更新时间、更新范围、更新次数和内容 revision 等元数据。
- 局部更新后明确标记“已局部更新”，详情可查看范围及扫描起止时间。
- 快照由不同时间采集的范围组成，不代表整个文件系统在更新时间的原子状态；对比页也应显示这一事实。
- 单个文件夹刷新成功不代表其余目录仍是最新，也不自动消除其他范围的未知状态。

## 4. 数据与接口设计

### 4.1 数据库迁移

实施时基于届时最新 schema 增量迁移；按当前 schema 4，预计进入 schema 5。不得删除旧库或要求用户清空快照。

建议增加以下数据，具体字段名可在实现时按现有命名统一：

| 数据 | 内容与用途 |
| --- | --- |
| `rescan_jobs` | task ID、snapshot/session ID、目标 node ID、原始路径、expected revision、状态、起止时间、错误、提交后 revision、性能指标 |
| `rescan_nodes` | 按 task ID 隔离的原始节点和目录结束状态，不作为公开 session 或 snapshot |
| `rescan_issues` | 暂存扫描问题，归属于 task ID |
| session 的节点 ID 分配水位 | 区分节点数量与最大已分配 ID；删除后也不复用历史 ID |
| 快照局部更新元数据 | 最近更新时间、更新次数；范围及详细历史可引用轻量任务记录 |

- 不把暂存任务写入普通快照列表或“最近扫描”列表，也不调用自动生成快照的 finalize。
- 暂存表沿用原始 BLOB 路径、身份和元数据语义，复用有界 `IndexConsumer` 链路；避免通过 JSON 传输整棵子树。
- 任务清理只删除该 task ID 所有的暂存数据，不影响其他任务或原快照。
- 保留轻量提交记录用于恢复和范围时间展示；成功、失败后按任务清理大体积暂存数据。
- 现有快照存储估算需说明扫描期间暂存空间的额外开销，不将暂存任务当成新增快照。

### 4.2 对外接口

建议新增专用异步控制接口，而不是将扫描副作用混入 `queryIndex` 的普通查询：

```text
startSnapshotRescan(snapshotId, nodeId, expectedRevision) -> taskId
getSnapshotRescan(taskId) -> 有界任务状态
cancelSnapshotRescan(taskId)
```

- 调用方只传索引身份与 revision，不传任意文件系统路径；服务端从受信任的索引解析原始路径字节。
- 接受请求前验证调用 UID、快照存在且可用、目标为目录、未保留、无冲突任务和 revision 一致。
- 复用现有前台服务的准备、启动及启动失败回收流程；增加任务类型，不能仅创建数据库任务后遗漏服务启动。
- 任务状态与最近一次全量扫描的 `ScanSnapshot` 分离，避免刷新历史快照时覆盖首页另一份扫描记录。
- Pigeon、生成桥接代码、Coordinator AIDL 和 Dart 客户端一同更新；状态返回沿用现有有界 JSON 风格即可。
- 第一版整个应用最多一个全量扫描或局部重扫任务；对当前目标的删除、保留状态变更等冲突操作返回 busy。

## 5. 核心执行流程

### 5.1 准备与只读扫描

1. 读取目标快照、目标目录、expected revision、原始路径及扫描身份，持久化任务记录。
2. 沿用原 Android 用户、普通/Root 后端、卷身份、挂载视图及统计规则；无法确认兼容时拒绝更新。
3. 从快照根路径和原始相对路径构造扫描目标，不做有损 UTF-8 往返。RootBackend 当前接收 String，需增加保留字节的内部入口。
4. 保持不跟随符号链接、不跨挂载和打开后身份核验的规则；验证路径解析不会因祖先替换或符号链接绕出原范围。
5. 对合法的同路径目录重建，可将其作为新目录内容更新；不能仅因 inode 与旧快照不同就一概拒绝，也不能因此跳过实时打开核验。
6. 使用当前优化后的扫描与传输链路，分批写暂存区；沿用 4096 动作导入策略和有界缓存，不持有完整目录树。
7. 深度按快照全局深度计算，检查合并后总节点限制；不能重置为子树深度 0 后绕过原限制。

如果目录已消失，或已变成文件/符号链接，第一版保留原记录并提示刷新父目录。不要仅凭一次 ENOENT 删除整棵旧子树；父目录完整扫描后，才通过父子树替换确认其消失或类型变化。

### 5.2 暂存校验

- producer 正常完成，协议完整，目标及所需目录已完整枚举。
- 不包含权限拒绝、I/O 错误、资源上限、取消、挂载变化或扫描期间身份/目录变化导致的不完整结果。
- 节点 ID、父子关系、路径、深度、计数和元数据通过现有协议及新增合并校验。
- 当前快照 revision、保留状态和扫描身份仍允许应用该结果。
- 校验不通过只结束任务并清理暂存，不修改目标快照。

本次子树完整与原快照全局完整是两个概念。原快照可以在其他范围仍为 Partial；最终状态应由合并后的原始记录重新计算。

### 5.3 子树替换与节点映射

在同一个普通 UID 写入流程中开启最终事务，并再次核验 expected revision 和保留状态：

1. 依据父子索引递归枚举旧子树，形成磁盘侧有界处理的成员集合；不得使用解码后的字符串 `LIKE 'path%'` 判断范围。
2. 删除旧子树对应的问题和待替换记录，保留树外原始元数据与树结构。
3. 保留选中目录本身的 ID、外部 parent 和全局位置；用新扫描根的原始元数据替换其内容。
4. 对新后代分配高于历史分配水位的 ID，通过临时映射表转换 parent 和 issue 引用，不复用已删除 ID。
5. 将子树相对路径映射到原快照根的相对路径；修正根名称、name key、深度和父节点，不拼接显示文本。
6. 写入新节点及必要问题记录，更新节点/问题数量和 ID 水位。

路径包含非 UTF-8 字节、控制字符以及 `a`、`a-`、`a2` 等近似前缀时，范围必须仍然准确。第一版无需为未变化的全部后代保留 ID；稳定路径匹配、选中目录 ID 保留和不复用 ID 优先。

### 5.4 去重、汇总与原子发布

第一版在同一最终事务中完成：

1. 从合并后的 `nodes` 重新初始化该快照的贡献值和完整性，清理旧去重派生结果。
2. 重算整个快照的 device/inode 归属，沿用最小原始路径规则和元数据冲突语义。
3. 从深到浅重新汇总目录自身占用、子项容量、问题及完整性，更新根统计。
4. 同步更新 session 与 snapshot 的 revision、容量、节点数、问题数、状态和局部更新时间。
5. 使相关对比缓存失效，并记录本任务已提交以及最终 revision。
6. 一次提交后，才向外发布新结果；随后刷新界面和适用的持久化 journal。

实现时必须拆分“计算 SQL”与“事务/发布控制”。现有 finalize 会分批提交、推进 revision 并创建快照，不能直接套用。重扫事务内的辅助方法不能独立提交或提前推进公开 revision。

其他注意事项：

- 重新初始化不能从旧 `aggregates` 延续已经归零的硬链接贡献或已变为 false 的完整性，否则 owner 切换和修复后的目录无法恢复正确结果。
- 新 ID 可能稀疏，不能继续把“节点数量”当成最大 ID 或依赖 ID 恰好为 `1..nodes`。
- 树外硬链接元数据可能与此次观察不同；沿用冲突/未知规则，不凭树内的新值伪造树外也已重新扫描。
- 只更新目标 snapshot/session；其他快照数据保持原样。对比缓存可以失效重建，但不得改变其他快照的源数据。
- 保留原全量扫描的指标；本次遍历、合并、去重和汇总计时写入任务记录，不混用为原扫描耗时。
- 第一版全快照 SQL 重算可能形成较长写事务，必须测量锁等待、WAL 增长、可取消性和界面查询延迟，不能直接承诺局部更新时间与子树大小严格成正比。

## 6. 并发、取消与恢复

### 6.1 状态机

```text
preparing -> scanning -> validating -> applying -> completed
preparing/scanning/validating/applying -> failed / cancelled / interrupted
revision 校验失败 -> stale
```

- `applying` 只有在事务提交前才能因取消回滚；提交后以 completed 为准。
- 取消需同时终止 producer、关闭 pipe、取消可中断 SQL 并结束当前任务，不能留下后台继续合并的工作。
- SQLite 提交后的任务记录和 revision 是完成依据。不能因后续通知、journal 或界面发布失败而宣称数据库已回滚。

### 6.2 并发控制

- 对扫描导入、局部合并、快照删除/保留、对比缓存构建等数据库写操作建立一致的串行化规则。
- 冲突请求返回可重试状态，不在 Binder 或主线程上执行长时间扫描、聚合或等待。
- 避免持有 Coordinator 的状态锁等待数据库任务，防止与回调或发布形成锁反转。
- 读取沿用 WAL 与 revision 检查；提交跨越一次多语句查询时，返回 stale-cursor 后重新查询。
- 同时失效内存对比构建器和磁盘缓存；提交前创建的构建器不能在提交后写回旧版结果。

### 6.3 进程与持久化恢复

- 暂存阶段死亡：旧快照保持不变，任务标为 interrupted，按 task ID 清理遗留暂存。
- 最终事务中死亡：由数据库恢复保证整体回滚或整体提交；启动后结合提交记录与 revision 判断结果。
- 提交后、journal 发布前死亡：识别已提交任务，重建或补发状态，不再次应用子树。
- 原快照保持可浏览状态，任务状态单独维护；不要调用会删除 snapshot 并设置 provisional 的现有 `interrupt()` 处理局部任务失败。
- 若目标是当前最近扫描，提交后更新其 journal 摘要；若不是，不覆盖另一 session 的 journal。
- 任务状态以数据库为准，journal 不参与跨文件原子性承诺；恢复时先对齐数据库 revision，避免新索引与旧摘要长期不一致。

## 8. 测试与验收矩阵

| 范围 | 必测场景与断言 |
| --- | --- |
| 基本变化 | 新增、删除、容量变化、空目录、目录与文件类型变化；结果与固定树全量重扫一致 |
| 范围隔离 | `a`、`a-`、`a2`、根目录、深路径、非 UTF-8 名称；树外原始节点不改写 |
| ID 与引用 | 连续刷新后 ID 不复用；选中根 ID 保留；parent、issue、详情和大文件引用有效；稀疏 ID 正确 |
| 硬链接 | 树内多个别名、树内外别名、旧 owner 删除、新 owner 路径更小、元数据冲突；全局归属及祖先统计正确 |
| 容量与完整性 | 稀疏文件、目录自身占用、软链接、跳过项、其他范围仍为 Partial、修复子树后完整性可恢复 |
| 目标变化 | 目标不存在、变成文件/符号链接、目录重建、祖先替换、挂载变化；不越界或将读失败当删除 |
| 失败与取消 | 权限拒绝、I/O 错误、资源上限、磁盘写满、各阶段取消；提交前快照内容及 revision 不变 |
| 并发冲突 | revision 变化、重复点击、全扫冲突、删除/保留冲突、对比构建跨提交；不误合并、不死锁 |
| 崩溃恢复 | 暂存中、合并中、提交后发布前杀进程；仅允许完整旧版或完整新版，无重复应用 |
| 对比与分页 | 旧游标失效，新 revision 可正常分页；快照摘要一致；对比缓存和内存构建器均失效 |
| 历史与迁移 | 各旧 schema 升级、受保留保护、其他快照不变、最近 journal 不串会话 |
| 界面 | 列表/树图/详情入口、进度/取消、定位恢复、局部更新时间、手机大字号及宽屏 |
| 回归 | 现有全量扫描、快照管理、增长对比、外部打开及优化策略不退化 |

正确性对照使用受控静态文件树及混合时间元数据回放。比较原始相对路径、类型、元数据、容量、按路径表示的 owner 与完整性；排除 session/node ID、采集时间和性能指标等非等价字段，保留文件本身 mtime。局部更新只保证范围内新元数据与树外保留记录合并后的统计正确；例如删除树内硬链接后，树外别名的旧 nlink 不必等于实时全扫值。完整规则见[步骤 1 契约](./snapshot-subtree-rescan-contract.md)。真实 `/data/data` 在变化，不能要求两次扫描逐项相等。

性能记录至少包括：子树及全快照节点数、遍历/传输、暂存导入、校验、替换、去重、汇总、最终提交、发布、端到端时间、锁等待、查询延迟、主库/WAL/暂存峰值和内存峰值。区分扫描工作与全快照 SQL 成本，不重复相加重叠阶段。

## 9. 后续优化与不在首版范围内的功能

- 只重算受影响的 device/inode 组，并沿所有相关祖先链更新统计；覆盖硬链接 owner 转移后再取代全快照重算。
- 如最终写事务过长，评估派生结果暂存与版本化发布；不以分批暴露半成品来换取低延迟。
- 多目录队列需合并重叠范围，解决版本冲突和取消边界后再引入。
- Partial 结果合并必须先定义每个已完整枚举范围的删除证据和未知覆盖，不能简单覆盖旧子树。
- 自动监控、定时重扫、文件内容哈希、重命名追踪、完整历史版本和提交后撤销均不属于本轮。
