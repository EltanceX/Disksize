# 扫描性能：测量、优化方案与实施步骤

日期：2026-11-17。方案对应代码基线：`fa211a9`，应用元数据协议 v3、SQLite schema 4。

本文保存后续性能工作的执行方案。历史实测与当前实现已经核对；新增分层基准、埋点和算法优化均待实施，本文不代表已经取得新的性能收益。

## 1. 问题与判断

用户观察到 TreeSize 约 5 秒扫描 C 盘 150 GB、15 万目录和 80 万文件，CPU 约 5%、磁盘约 300 MB/s；DiskSize 扫描约 18 GB、19 万条目需三十多秒，CPU 平均超过 90%。

文件系统、硬件、权限和缓存会影响结果，但现有记录也显示 DiskSize 的数据库导入与最终聚合有明确的优化空间。不能将差距全部归因于 NTFS 与 Android 文件系统。

- TreeSize Free 的[官方 Microsoft Store 页面](https://apps.microsoft.com/detail/XP9M26RSCLNT88?hl=en-US&gl=US)说明其直接使用 MFT（Master File Table）。集中读取文件系统元数据与逐目录枚举、逐项查询 metadata 的成本不同；用户此次扫描的版本、权限和具体模式仍需记录，不能直接认定使用了哪条路径。
- 本机 Root 全局挂载视图中的 `/data`、`/data/data` 实测为 **F2FS**，不是 ext4。普通应用的隔离视图、Root 全局视图及 `/storage/emulated/0` 的 FUSE 入口应分别测量，证据见 [Root 挂载视图](./root-mount-namespace.md)。
- 容量扫描主要读取目录项和文件元数据，不读取那 150 GB 或 18 GB 的文件内容。核心吞吐口径是条目/秒，文件容量仅作为样本特征。监控中的磁盘 MB/s 还受元数据预读、缓存和其他进程影响。
- Windows 与 Android 工具的 CPU 百分比可能分别按全部逻辑处理器、单核计算。应先比较 CPU 秒、核数和统计范围，不能直接比较 5% 与 90%。
- Debug 与优化构建分开记录。Flutter profile 不能自动证明 C++ 已启用优化，应核对实际产物对应的 `compile_commands.json` 与编译、链接参数。

本轮目标是先定位时间和资源消耗，再逐项降低端到端耗时、CPU 秒和索引成本；不预先承诺达到 TreeSize 的 5 秒。

## 2. 当前链路与候选瓶颈

当前应用链路：C++ 流式扫描 → v3 二进制协议 / pipe → Kotlin 校验解码 → 普通 UID SQLite → 硬链接去重 → 目录聚合 → journal 终态发布 → 界面读取。

| 环节 | 当前实现 | 待验证的优化假设 |
| --- | --- | --- |
| 遍历 | 单线程 DFS，逐项 `readdir`、`fstatat`，再查询 mount ID；目录打开后另做身份核验 | 元数据和 mount ID 查询可能合并，减少重复系统调用 |
| 传输 | 通常最多 256 条或约 32 KiB 一批，单帧 payload 上限 64 KiB；目录关闭、问题和进度会触发 flush | 短批次、编码和分配可能增加开销 |
| 消费 | 同步解码和写库，消费者变慢会阻塞 pipe 与 producer | 扫描计时包含写库背压，不能直接当成纯遍历成本 |
| 导入 | 每节点写 `nodes` 和 `aggregates`；最多 256 个导入动作提交，进度也会触发提交 | 事务、双表和多个索引的写放大可能是主要成本 |
| 记录 | 完整路径 BLOB、两表中的名称十六进制 key、重复会话 UUID | 记录和索引体积偏大，编码与对象分配可精简 |
| 最终处理 | 所有有效非目录项按身份分组，随后批量更新 owner、容量和完整性，再从深到浅汇总 | 去重、重复更新和目录汇总可能产生大量数据库访问 |

`nodes` 当前有 3 个二级索引，`aggregates` 有 8 个二级索引，均不含主键。删除或延迟构建索引需要同时检查查询、去重、聚合和旧快照的使用情况。

对应实现：

- [流式扫描核心](../android/app/src/main/cpp/core/stream_scanner.cpp)、[文件系统与 mount 查询](../android/app/src/main/cpp/core/filesystem.cpp)。
- [native 协议发送](../android/app/src/main/cpp/jni/index_protocol.h)、[普通模式 pipe](../android/app/src/main/kotlin/com/example/disksize/index/LocalScanPipe.kt)、[协议接收](../android/app/src/main/kotlin/com/example/disksize/index/IndexProtocol.kt)。
- [SQLite 导入、去重与聚合](../android/app/src/main/kotlin/com/example/disksize/index/IndexStore.kt)。

以上是代码和历史计时支持的候选方向，尚不能替代当前版本的 profiler 结果。

## 3. 历史基线与计时口径

### 3.1 真实应用目录

历史设备：Xiaomi sheng / Pad 6S Pro，Android 16 / API 36、arm64、KernelSU，SELinux Enforcing。Root 全局视图扫描 `/data/data`，F2FS，188,441 个节点，逻辑容量 18,475,537,774 B，报告占用 18,971,312,640 B。

| 历史指标 | 时间 | 解释 |
| --- | ---: | --- |
| 会话时间 `endedAtMillis - startedAtMillis` | 33.881 s | 持久化会话起止时间差；并非从点击按钮到界面完成的计时 |
| `scanMicros` | 20.659045 s | producer 扫描、同步发送及消费者背压所在的流水线区间 |
| `importDbMicros` | 19.004654 s | 消费者导入数据库操作的累计经过时间，与流水线重叠 |
| `finalizeMillis` | 13.164 s | 最终处理区间，包含下面两个子阶段 |
| `dedupMillis` | 4.879 s | 硬链接身份分组等去重阶段 |
| `initializeMillis` | 1.405 s | owner、别名容量和完整性等初始化更新 |

结果为 completed、complete=true、0 个问题，扫描结束时 FD 为 0。来源为本机忽略文件 `.local/root-namespace/app-data-result.json` 和 [Root 实测记录](./root-mount-namespace.md)。

**不能将 `scanMicros` 与 `importDbMicros` 相加，也不能把两者之差当成纯遍历耗时。** 两项均是经过时间，不是 CPU 时间；`dedupMillis`、`initializeMillis` 已包含在 `finalizeMillis` 中。最终处理现有计时也不覆盖随后所有发布开销，后续应补齐独立的端到端计时。

旧文档中的约 37.20 秒是整项 instrumentation 测试时间，含测试开销，与 33.881 秒会话时间属于不同口径。约 19 秒的导入计时支持优先调查数据库，但尚未精确说明 CPU 花在哪些函数中。

## 4. 测量方案

### 4.1 复用同一核心的三种模式

新增以下三种基准模式，**均待实现**。三者必须复用应用实际使用的 `stream_directory`、扫描配置与统计语义。

| 模式 | 包含工作 | 用途 |
| --- | --- | --- |
| A：纯流式遍历 | 真实扫描，回调仅做有界计数和轻量摘要；不输出逐节点日志、不写库 | 测量元数据遍历与必要校验的成本 |
| B：遍历与传输 | 与应用一致的协议编码、pipe、校验和解码；有界计数消费者替代数据库 | 测量协议、跨线程/进程传输和对象分配成本 |
| C：完整链路 | 真实服务、SQLite 导入、去重、聚合、journal 终态发布 | 评估用户可见收益及各阶段成本 |

普通与 Root 后端分别运行；Root 模式要保留实际 root producer → 普通 UID 消费者的边界，A 模式也应记录实际 UID、挂载视图及启动开销。

现有 [原型 CLI](../native_tests/scan_cli.cpp) 使用旧 `scan_directory`，会持有全树，不能直接作为模式 A。模式 B 需将接收器的消费接口与具体 `IndexStore.Import` 解耦，但保留同等协议校验和错误处理。

另增加可选的固定元数据流回放：将同一份合成或脱敏元数据分别写入不同实现，隔离 SQLite 导入与聚合成本。回放只能说明持久化性能，不能代替真实扫描。模式间耗时差用于定位假设，仍需结合独立埋点、背压与 CPU 采样解释。

### 4.2 时间与资源埋点

新增持续时间使用单调时钟，跨进程通过各自的耗时、事件及 trace 关联；墙上时间保留用于会话展示。保留旧指标原义，新增字段需注明单位和是否重叠。

| 范围 | 需记录的指标 |
| --- | --- |
| 启动与端到端 | 用户请求到可浏览终态；权限/Root 冷启动、服务连接、扫描开始、最后一帧、最后导入提交、最终处理结束、journal 发布及 UI 更新分别打点 |
| producer | 节点/目录/文件/链接/问题数，纯扫描回调模式耗时，协议编码耗时，pipe 写等待，帧数、字节数与平均/最大批量 |
| consumer | 读等待、校验解码、导入操作和提交耗时；事务数、每事务动作数、短事务原因、父路径缓存命中及 GC/分配情况 |
| 最终处理 | 去重分组、owner/容量初始化、目录汇总、最终数据库提交、快照与 journal 发布，分别计时 |
| 存储 | 主库/WAL 起止及峰值，受控 checkpoint 前后大小，临时库体积，进程 I/O 字节；明确逻辑写入量与实际设备写入量的区别 |
| 资源 | producer、普通扫描服务、UI 各进程的 user/system CPU 秒、RSS/PSS、FD 峰值与结束值；必要时细到线程 |
| 交互 | 目录与大文件首页/末页延迟、扫描期间查询延迟、取消到资源释放的延迟、快照对比查询延迟 |

耗时嵌套关系必须随报告记录。例如导入操作已包含部分提交时间时，提交耗时仅作为子项展示，不能再相加。pipe 写调用的经过时间包含阻塞及少量复制开销，不能直接当成遍历 CPU 时间。埋点采用批次累计和限频采样，避免逐节点日志或无限事件列表改变被测负载。

CPU 统一提供原始 CPU 秒与两种换算：

- 单核口径：`进程 CPU 秒 / 墙钟秒 × 100%`，多线程进程可能超过 100%。
- 全机口径：上述结果再除以记录的逻辑处理器数量；同时记录在线核数、频率与温度/降频状态。

进程合计不要再加其线程明细，避免重复统计。Root 进程、普通服务和 UI 的总成本分开列出，再按互不重叠的进程求和。

### 4.3 样本与对照条件

1. 固定设备、系统/内核、ABI、应用提交、APK 哈希、构建类型、实际 native 优化参数、SQLite 配置。为优化构建保留可符号化的采样资料。
2. 固定入口路径、实际文件系统、UID、用户解锁状态及挂载 namespace；记录同设备 bind mount、跳过规则和完整性，避免因少扫目录获得虚假加速。
3. 受控规模覆盖 1 万、10 万、100 万条目，另测浅宽树、深树、长路径、非 UTF-8 名称、硬链接、稀疏文件、错误/不可读项、扫描中变化和跨挂载。FUSE 与直接 F2FS 入口单列。
4. 每个固定样本保存 manifest 或稳定摘要，以及各类型数量、最大深度/路径长度、逻辑/占用、问题数和完整性。计数含不含根节点需明确；历史规模样本含根节点，故为 10,001 等。
5. 固定样本的索引输出放在样本树外，避免扫描自己的增长。实时 `/data/data` 包含 DiskSize 自身数据库且其他应用也会写入，应单独报告，不能当成不变样本或强求每次容量一致。
6. 冷热缓存分开。预热后的重复测试标记为热缓存；重启服务不等于冷缓存。不默认执行全机 `drop_caches`，无法控制时标注缓存状态未知。记录充电、电量、温度和后台活动。
7. 先预热，再做至少 5 次有效重复，交错 A/B 版本顺序，减少缓存与温度偏移。报告中位数、最小/最大值和原始次数；少量样本不宣称可靠 P95。
8. 样本生成/删除、安装、首次 Root 授权及服务启动单列，既不混入核心扫描计时，也不从用户感知总时间中悄悄省略。采样运行与未采样运行分别记录工具开销。

固定样本用于严格正确性及性能对照；实时应用目录用于验证真实负载。后者是时间区间观测，允许出现诚实的 Partial 和变化问题。

### 4.4 工具与结果保存

优先在权限与设备能力支持时使用 simpleperf 定位 native/JVM 热点、Perfetto 观察调度/等待/GC/磁盘活动。必要时用 strace 汇总 `getdents64`、`newfstatat`、`statx`、`openat` 等调用数量及耗时；跟踪工具的额外开销必须有未跟踪对照。

原始 JSON、trace、编译参数、采样与详细日志放入忽略目录 `.local/scan-performance/`，文档仅保存脱敏摘要与结论。默认不记录真实应用的逐项路径，不读取目标文件内容。指标 JSON 应带独立版本，字段缺失时标为未测，不能以 0 代替。

## 5. 优化优先级与实现方案

### P0：补齐可比较的基线

先实现三模式基准、阶段埋点和结果导出，在实际启用 native 优化的构建上重测当前实现；Debug 留作回归。确认扫描、背压、导入和最终处理各自成本后，按当前热点调整后续顺序。

交付物：可复现入口、固定样本摘要、编译参数证明、各阶段计时与资源报告。没有这组对照前，不将猜测写成已确认的 CPU 瓶颈。

### P1：降低 SQLite 导入与记录成本

1. 先统计事务数和短事务来源。在有界动作数与最大提交间隔下，对比 256、1,024、4,096 等批量；协议批次与数据库事务大小独立调整。检查进度触发提交是否过频，保留 revision、可见性和中断恢复语义。
2. 记录每个索引的用途与 `EXPLAIN QUERY PLAN`，优先消除重复工作、无效更新和重复名称编码；复用已编译语句，降低逐项绑定集合、装箱和临时数组分配。
3. 测量双表写入及 11 个二级索引的实际成本，再评估精简索引、导入 staging 或会话局部索引方案。当前所有会话共享表，不能在新扫描期间直接全局删除排序索引，使旧快照查询退化；重建成本也需计入总耗时。
4. 若存储仍为热点，再评估内部整数会话键、原始字节排序键、路径前缀/父子表示等紧凑记录。此类方案需测量详情路径重建和增长对比的成本，避免把写入成本转移到查询。
5. schema 变化必须提供非破坏迁移及中断恢复策略，核对旧快照、保留标记、删除、空间估算和 diff cache。现有快照大小按库空间分摊，不能拿该估算代替基准中的主库/WAL 实测。

每次只改变一个因素，统计条目/秒、CPU 秒、主库/WAL、首末页与扫描期间查询延迟、取消延迟。不能只看导入变快而忽略随后建索引或最终聚合变慢。

### P2：减少去重与目录聚合工作

1. 用固定流回放覆盖无硬链接、少量/大量硬链接、乱序 owner、同 inode 元数据变化和深宽树，区分身份分组、owner 更新与目录汇总热点。
2. 优先优化查询计划、批量关系运算和重复更新，评估让普通单项身份组少走额外写入路径；保留批次上限与取消检查。
3. 目录汇总评估按父目录/深度批量聚合，减少逐节点关联查询。若考虑在目录关闭时预聚合，必须处理后发现的硬链接 owner、目录替换、错误回撤和完整性传播，不能提前固定最终容量。
4. 清理临时去重数据、维护查询索引及最终发布的成本均纳入完整链路，不将其移到计时区间之外。

不能仅依赖 `nlink > 1` 排除其余身份：同身份冲突、别名及扫描中变化仍需按现有规则处理。owner 必须继续由最小原始相对路径字节顺序确定，与发现顺序无关；非 owner 保留 metadata、容量贡献为 0，变化问题及未知范围照常传播。

### P3：减少系统调用及协议分配

1. 统计当前逐项 `fstatat` 加 `statx` 的调用次数、回退频率和耗时，先验证其占比。
2. 设计统一元数据查询接口：支持时用一次 `statx` 返回所需 metadata 和 mount ID，逐字段检查返回 mask；不支持或字段不足时保留兼容回退。
3. 保留目录 `openat` 后的身份/挂载核验及结束时变化检测。`dirent.d_type` 只能作为提示，不能替代容量、身份或挂载信息，也不能在竞态下改变不跟随链接语义。
4. 对编码 buffer、解码对象、路径拼接和名称 key 做有界复用，测量收益；需要时再调整帧批量、目录关闭和进度 flush 策略，保留事件顺序与帧大小校验。

若协议格式或桥接接口发生变化，明确版本与兼容策略，同步更新发送、接收、Root 两侧及相关生成代码。若 native 热点占比很低，则将工作留到数据库优化之后。

### P4：最后评估有界并发

仅在消费者背压已经缓解、模式 A 显示遍历仍是主要耗时后，对比 1、2、4 个 worker。队列、buffer、目录 FD 和总内存必须有明确上限，保持目录身份及挂载语义。

并发需要重新验证父先于子、ID 分配、目录关闭事件、取消与硬链接确定性；不能依靠发现顺序决定最终归属。若吞吐收益不足以覆盖 CPU、内存、FD 和发热成本，保留单线程。原始块设备/离线解析 F2FS 或 ext4 不作为本轮实现路径。

## 6. 建议实施顺序与阶段交付

以下检查项均尚未完成；按小提交执行，每步附结果与回退结论。

- [ ] **步骤 1：测量契约。** 固定指标名称、单位、嵌套关系、开始/结束边界及报告版本；补充 producer、consumer、最终处理与发布计时，默认限频。
- [ ] **步骤 2：基准入口。** 基于 `stream_directory` 实现 A/B/C 和固定流回放，建立受控样本摘要；支持显式选择模式/后端与输出目录并记录实际 UID，样本仅在自有测试目录创建和清理。
- [ ] **步骤 3：优化构建基线。** 核验编译参数，先做 1 万条目冒烟，再完成 10 万和 100 万规模、普通/Root 与直接文件系统/FUSE 对照；真实应用目录作为独立 opt-in 项。
- [ ] **步骤 4：导入改进。** 依次 A/B 测试事务、编码/绑定分配、索引与记录布局。先做低风险调整，只有证据支持时引入 schema 迁移。
- [ ] **步骤 5：最终处理改进。** 优化去重与目录汇总，核对 owner、容量、问题及完整性；计入索引维护和最终发布成本。
- [ ] **步骤 6：native 与传输改进。** 根据重测热点合并 metadata 调用、降低编解码开销；仅在条件满足时增加有界并发实验。
- [ ] **步骤 7：整体验收。** 同构建、同样本和缓存条件复测，补充当前 schema/protocol 的性能结果文档、设备限制与回退方式，再决定采用哪些优化。

每步评审以证据决定是否进入下一步，不要求所有候选优化都落地。新方案若无稳定收益或破坏资源/交互边界，应撤回该项实现并保留测量结论。

## 7. 正确性与性能验收

### 7.1 所有优化的前置条件

- 保持只读扫描目标、不跟随链接、不跨挂载、目录打开后身份核验及变化检测；保留原始字节路径、稀疏文件与目录自身 blocks 的统计规则。
- 硬链接结果与发现顺序无关；固定样本逐项核对 owner、逻辑容量、报告占用、问题和完整性。未知/部分范围不能变成确定的零值。
- 取消、服务/Root 进程死亡与中断恢复正确；运行中、取消、失败或中断的会话不能发布可用终态快照，Partial 快照保留未知范围语义，terminal journal 发布顺序保持一致。
- Root 只读取元数据并写 pipe，数据库仍由普通 UID 持有；客户端 UID、协议版本、长度和畸形输入检查保持有效。
- 保持帧、队列、缓存、FD 和内存有界；现有最大 2,000,000 节点、512 层深度规则改变时，应另行评估并更新扫描身份/对比兼容性。
- 旧快照、保留状态、批量删除、增长对比、稳定分页和 stale-cursor 语义通过回归；64 位容量溢出不能静默截断。
- 测试采用覆盖安装保留数据，不卸载应用或自动清空真实快照。基准清理只操作明确归属于该次测试的样本、会话或独立测试库。

### 7.2 性能采纳标准

基线与候选实现只包含待验证的改动，使用相同构建配置、设备、样本与缓存条件做单变量 A/B。收益需超过重复运行噪声，报告中位数及范围；最终以完整链路耗时判断，不以某一子阶段单独变快判断成功。

同时核对 CPU 秒、RSS/PSS、FD、主库/WAL、目录/大文件/快照对比查询、取消延迟。出现明显退化时先定位并重测，不能仅因扫描秒数下降就采纳。具体数值预算由步骤 3 的当前版本基线确定，不把历史 Debug 数据或 5 秒作为性能承诺。

## 8. 现有工具与待新增工具的边界

现有 [阶段 5 规模入口](../tools/phase5/verify.ps1)支持 1 万、10 万、100 万文件规模和 ordinary/root 后端；[设备测试](../android/app/src/androidTest/kotlin/com/example/disksize/index/IndexDeviceTest.kt)中的 `realFileScaleBaseline` 提供真实文件基准。用法见 [阶段 5 工具说明](../tools/phase5/README.md)。

该脚本使用 **Debug instrumentation 和完整入库链路**，目前没有 A/B/C 模式、固定流回放或优化构建性能报告；它直接使用 `adb install -r`，也没有 `RootInstall` 参数。需要 Root 覆盖安装时，使用现有 [安装工具](../tools/install-android-apk.ps1)的 `-UseRoot`，不要将尚未实现的参数写入执行命令。

`rootAppDataUsesGlobalMountNamespace` 是显式 opt-in 的真实 `/data/data` 回归，需要 `rootAppData=true` 及 `rootMountNamespace` 参数，见 [Root 测试步骤](./root-mount-namespace.md)。它会保存真实索引，并非无持久化的纯扫描基准。

建议新建 `tools/scan-performance/` 作为统一性能入口，负责构建核验、模式选择、采样、重复执行、结果导出和摘要生成；此目录及其命令行接口目前尚未实现。正确性回归优先复用现有 native 流式测试、协议测试、索引测试及阶段 6/8 设备验证，按实际修改选择范围。

## 9. 每次实验的报告模板

| 项目 | 填写内容 |
| --- | --- |
| 实验身份 | 日期、基线/候选提交、唯一改动、APK 哈希、schema/protocol、结果版本 |
| 环境 | 设备、系统/内核、ABI、构建类型/native 参数、SQLite 配置、核数、温度、缓存状态 |
| 扫描视图 | 模式 A/B/C/回放、ordinary/root、入口、实际 FS、UID、mount namespace、跳过规则 |
| 样本 | 固定样本摘要或实时负载说明、总节点/各类型数、深度/路径长度、容量、问题与完整性 |
| 运行 | 预热次数、有效/失败次数、逐次原始结果；采样工具及未采样对照 |
| 时间 | 启动、流水线、导入及提交子项、去重、初始化、目录汇总、发布、端到端；注明重叠 |
| 资源 | 各进程 CPU 秒/占比口径、RSS/PSS、FD、GC、pipe 等待、帧/事务数、主库/WAL/临时空间 |
| 查询与恢复 | 首页/末页、扫描期间查询、快照对比、取消与进程中断结果 |
| 结论 | 中位数/范围、相对变化、正确性核对、限制、采纳/回退决定、后续假设 |

未采集的项目填写“未测”并说明原因。保留失败和 Partial 结果的原因，不通过只展示最快一次或减少扫描范围证明加速。
