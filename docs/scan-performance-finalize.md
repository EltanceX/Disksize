# 扫描性能：步骤 5 最终处理改进

2026 年 11 月 18 日。最终处理只为共享的文件身份建立 owner 记录，按深度从底向上只汇总目录。100,001 节点普通模式的完整扫描中位数从 11.563 秒降到 6.870 秒（减少 40.6%）。最终处理阶段从 5.013 秒降到 0.379 秒。

## 实现与规则

- 通过现有 `(sid,device,inode,path)` 索引按身份分页。统计同身份的全部条目；只有元数据有效、未跳过的非目录参与 owner 选举和变化检查。单条目身份保留入库时的 owner 和容量，不写 `hardlinks`；一个合格条目加一个失效别名也算共享身份。算法不依赖 `nlink`。
- 共用身份由最小的原始路径字节串决定 owner，仍比较大小、分配空间、mtime 秒和纳秒。沿用非 owner 容量归零、保留原 metadata、给变动组报告问题且传播不完整状态的规则。目录自身占用仍独立于 owner。没有共享身份时直接跳过 owner 应用。
- 批量分组只读身份索引中下一边界前的行，最多 4,095 条。边界身份单独用可取消查询处理，因此不会把大型硬链接组拆开。owner 应用每批最多 4,096 个 ID；目录汇总每批最多 1,024 个目录。单个很宽目录仍需在一次 SQL 中读取它的子项。
- 入库已写入叶节点自身容量与完整性，处理硬链接后叶节点无需重算。每个目录扫描一次已处理子项，同时得到逻辑、分配容量和完整性；保留两类 64 位溢出检查。按目录批次检查取消，已提交的数据仍为 provisional，最终快照和 journal 的发布顺序不变。
- schema 4、协议 v4、索引和快照兼容性规则均不变。新快照仅保留实际共享身份的去重工作记录，随快照删除；旧快照不会重算或重新压缩。

## 完整扫描：100,001 节点普通模式

与[步骤 4](./scan-performance-import.md)使用同一台 Xiaomi sheng（Android 16、F2FS、arm64），Profile 构建的 native 核心为 `-O2`。每组预热 1 次、正式运行 5 次，交错使用同一空文件树、同一个 APK、同一 `4096-eager-list` 导入策略和新建的独立基准库。没有清空文件系统缓存，没有访问实时 `/data/data`。

下面的四组用于分离去重与目录策略的收益。组合方案随后进一步把分页边界的身份改为可取消查询，再用有硬链接的回放和 Root 完整链路复验。表内数值为独立中位数，单位为秒；最终处理为去重、owner 初始化和汇总之和，完整扫描还包含终态提交、预览和 journal 发布。

| 策略 | 完整扫描［最小，最大］ | 最终处理 | 去重 | 初始化 | 汇总 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `baseline` | 11.563 [11.456, 11.862] | 5.013 | 1.940 | 0.719 | 2.367 |
| `dedup` | 9.165 [9.081, 9.251] | 2.569 | 0.264 | <0.001 | 2.305 |

旧策略与组合方案的导入中位数分别为 5.596、5.505 秒；节省的时间主要来自最终处理。终态主库为 93.43、90.31 MiB，WAL 均为 0.50 MiB。大文件首页/末页中位数分别为 47.97/25.69、49.15/13.66 毫秒，首页范围重叠。

## 固定流回放

回放验证相同元数据写入后得到的快照语义，分离遍历、pipe 和 journal。每个配方预热 1 次，正式运行 3 次。跨目录的 owner 路径在较晚一半才遇到；设置 `nlink=1`，用于验证算法不会依赖链接计数猜测身份唯一。稀疏与密集样本分别有 387 和 49,500 个共享身份，其中 23 和 2,912 个发生元数据变化。

总量与预期独立核对；计时停止后按 ID 分页对照每行的 owner、容量、完整性和问题节点、代码、errno，确认相同配方的结果摘要一致。密集样本两种策略都得到 655,148 逻辑字节、29,444,096 分配字节和 5,824 个问题，状态为 `partial`。

| 配方 | 节点 | 回放总时间 基线 → 优化［范围］（秒） | 最终处理 基线 → 优化（秒） | 回放进程 CPU 基线 → 优化（秒） |
| --- | ---: | ---: | ---: | ---: |
| 稀疏硬链接 | 100,001 | 10.940 [10.078, 10.959] → 6.434 [5.768, 6.498] | 5.248 → 0.781 | 8.980 → 5.658 |
| 密集硬链接 | 100,001 | 10.520 [9.946, 10.550] → 8.158 [7.755, 8.220] | 4.780 → 2.418 | 8.565 → 6.767 |
| 深宽树（101 层，单目录 9,900 个子项） | 10,001 | 1.568 [1.277, 1.616] → 0.974 [0.958, 0.993] | 0.616 → 0.068 | 1.582 → 1.183 |

密集样本的初始化中位数由 1.347 增至 1.776 秒，终态主库由 91.11 增至 93.60 MiB。该配方的别名密度最高，需要实际替换大量聚合行并维护索引；去重及汇总的节省仍使整体变快。稀疏组的主库由 94.28 降至 91.30 MiB，不能将容量变化外推至任意真实树。

## 最终构建的独立 Root 采样

100,001 节点内部 F2FS 固定树。每组预热 1 次、正式运行 2 次；开启每约 1.2 秒的独立采样。SQLite 仍在普通 UID 的服务中执行，两组都返回 0 逻辑字节、4,136,960 分配字节和 0 个问题。

| 指标 | `baseline` | `optimized` |
| --- | ---: | ---: |
| 完整扫描［最小，最大］（秒） | 11.394 [11.351, 11.436] | 6.824 [6.823, 6.826] |
| 最终处理（秒） | 4.862 | 0.386 |
| 服务 / Root 扫描进程 CPU（秒） | 8.44 / 0.50 | 4.87 / 0.47 |
| 服务 RSS / PSS（MiB） | 204.40 / 110.59 | 208.64 / 114.48 |
| 服务最大 FD（两次范围） | 126–126 | 126–127 |
| 采样 WAL 最大长度（MiB） | 3.35 | 3.29 |
| 终态主库 / WAL（MiB） | 93.52 / 0.50 | 90.40 / 0.50 |
| 大文件首页 / 末页（毫秒） | 37.53 / 14.46 | 43.48 / 15.80 |

CPU 秒是窗口内首末两个样点的差，样点跨度由 10.55 降到 6.12 秒，不能据此换算整机 CPU 占比。内存列为单次采样峰值的中位数，RSS/PSS 两次运行的范围重叠；Root 扫描器峰值 FD 均为 96。主库采样最大长度为 97.54/88.22 MiB，后者小于终态主库，说明采样漏了最后一段增长。Root 组首页略慢但范围仍有重叠；小样本不能据此判定查询延迟的变化。

## 正确性与回退

Debug 构建、Android Lint 和 4 个 JVM 协议测试均通过。

真机 Profile 共报告 35 项，32 项通过、3 项未启用（额外 Root fixture、实时 `/data/data` 与旧规模入口）。覆盖同身份组跨过 4,096 条边界、原始字节路径顺序、失效及跳过别名、同 inode 元数据变化、目录共享身份、容量 SUM 和自身占用加法溢出、汇总阶段取消、进程死亡后恢复、旧快照和增长对比。在一次 10,101 节点生命周期回归中，导入期间目录查询为 31.0 ms，取消到观察到终态为 41.1 ms；单次观测不代表延迟分布。

最终 Profile 构建的 10,001 节点 A/B/C/Replay 冒烟通过；C 和 Replay 均报告默认 `optimized`。测试后恢复原主 APK 和测试 APK，并核对两者的 SHA-256。如果需回退，将 `FinalizePolicy.DEFAULT` 改为 `BASELINE` 后构建即可；已有结果和保留快照无需迁移。

原始 `environment.json`、逐次报告、仪器测试日志、编译参数和采样留在 `.local/scan-performance/step5-*/`；普通四组对照见 `step5-full-100k/`，最终 Root 对照见 `step5-root-resources-100k/`。普通四组对照主 APK SHA-256 为 `1EBE9D05B789A9C6B703EE68D99534BBA9A5B7FC6C518631C85BB9DD4645B7FC`，最终构建为 `69C33CAC756CFD95ABBC68BA9880CE3B50AD734297EF78C769E588561E142926`。真实目录、百万规模和接近节点上限的内存仍留待整体验收。
