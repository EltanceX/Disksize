# 扫描性能：步骤 4 导入改进

2026 年 11 月 18 日。默认事务上限从 256 提到 4,096 个导入动作；进度帧仍在提交后发布，结束帧仍提交尾批。100,001 节点的完整扫描中位数从 16.384 秒降到 11.393 秒（耗时减少 30.5%）。协议 v4、SQLite schema 4、绑定方式和索引均保留。

基于[优化构建基线](./scan-performance-baseline.md)分别比较事务大小、进度帧触发提交、语句绑定和二级索引。测试使用同一台 Xiaomi sheng（Android 16、arm64、8 个在线逻辑核）和同次运行的 Profile APK，native 为 `-O2`。使用内部 F2FS 的固定空文件样本与独立 WAL 基准库，未清除文件系统缓存，也未访问实时 `/data/data`。

同一组内交错测试，每个变体预热后单独统计；耗时单位为秒。`256-eager-list` 对应步骤 3 的提交和绑定策略，重新测得的同批对照是百分比计算的分母。回放不产生进度帧，只用于分离持久化成本；是否启用改动以完整服务链路为准。运行和重现参数见[工具说明](../tools/scan-performance/README.md)。

## 对照因素

- 动作上限为 256、1,024 或 4,096；动作包括节点、目录关闭、问题、卷容量记录。协议帧仍最多 256 节点，与数据库事务上限独立。
- `eager` 保持每个进度帧尝试提交，SQLite 提交完成后才报告这一帧的进度。`paced` 在省略提前提交时仍提供已发现进度，按动作或进度帧检查 250 ms 活动窗口；不是 SQLite 或 pipe 阻塞时的定时承诺。summary 始终提交划定终态。
- `typed` 在复用 SQLite 语句的基础上按字段绑定，名称编码只算一次，并用单个数组拼接原始路径。`list` 保留原 `bindAll`。
- 仅 `-lean` 变体的独立测试库省略 `node_parent`。查询、聚合和旧快照共用其它索引；不在导入中动态拆装索引。

## 固定流回放：100,001 节点

每组预热 1 次，测量 5 次。总时间为中位数 `[最小值, 最大值]`，其余为独立中位数。导入包含提交。

| 变体 | 总时间（秒） | 导入（秒） | 提交（秒） | 事务数 | 主库（MiB） | 回放进程 CPU（秒） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `256-eager-list` | 15.466 [15.161, 15.881] | 10.046 | 4.694 | 395 | 92.20 | 10.82 |
| `1024-eager-list` | 11.771 [11.653, 11.858] | 6.425 | 1.976 | 99 | 92.20 | 9.46 |
| `4096-eager-list` | 10.523 [9.650, 10.683] | 5.384 | 1.264 | 25 | 92.20 | 8.71 |
| `1024-eager-typed` | 11.839 [11.681, 12.012] | 6.405 | 2.053 | 99 | 92.20 | 9.30 |
| `4096-eager-typed` | 10.426 [10.326, 10.539] | 5.193 | 1.274 | 25 | 92.20 | 8.60 |
| `1024-eager-typed-lean` | 11.568 [11.489, 11.878] | 6.225 | 1.924 | 99 | 86.90 | 9.22 |

增大批量的收益明显。`typed` 在两种批量下的总时间范围仍与同批量的 `list` 重叠，收益小且方向不一致。减少一个二级索引节省了 5.30 MiB（约 5.7%），但本次耗时差仍在变体的运行波动内。没有为这些变化引入正式库迁移。所有回放组终态 WAL 都为 0.50 MiB。

## 完整链路 C：100,001 节点

普通 UID，每组预热 1 次、测量 5 次。总时间从准备扫描计至终态发布；查询是发布后的 Binder 请求。以下各列分别取中位数。

| 变体 | 总时间（秒） | 导入（秒） | 其中提交（秒） | 事务数 | 大文件首页 / 末页（毫秒） |
| --- | ---: | ---: | ---: | ---: | ---: |
| `256-eager-list` | 16.384 [16.311, 16.958] | 10.294 | 4.867 | 425 | 41.69 / 14.17 |
| `1024-eager-list` | 12.739 [12.635, 12.972] | 6.763 | 2.191 | 118 | 43.40 / 13.19 |
| `4096-eager-list` | 11.393 [11.311, 11.617] | 5.520 | 1.506 | 42 | 40.38 / 12.26 |
| `4096-paced-list` | 11.363 [11.265, 11.451] | 5.415 | 1.322 | 26 | 41.77 / 13.02 |

默认方案每秒由约 6,104 增至 8,777 节点。导入耗时少 46%，pipe 等待可写由 10.934 降到 6.043 秒，去重和目录汇总基本不变。各组终态主库均为 93.53 MiB、WAL 为 0.50 MiB。`eager` 的 4,096 组中位数有 41 次提交由进度帧触发，最长事务活动时间的中位数是 217 ms。`paced` 组每轮合并约 38 次进度提交，但端到端中位数仅再少 30 ms，区间重叠，跳过提交时显示的进度可能领先于已可查询的条目，因此仅保留为基准选项。

## 独立 Root 资源采样：100,001 节点

Root 进程遍历同规模内部固定树；SQLite 仍由普通 UID 的服务写入。每组预热 1 次、测量 2 次，每约 1.2 秒采样。表中为两次正式运行的中位数；CPU 秒基于窗口内首末样点，内存、FD 和文件长度是样到的峰值。

| 指标 | `256-eager-list` | `4096-eager-list` |
| --- | ---: | ---: |
| 总时间（秒） | 16.470 [16.393, 16.547] | 11.281 [11.247, 11.314] |
| 导入服务 CPU（秒） | 10.94 | 8.31 |
| Root 扫描进程 CPU（秒） | 0.62 | 0.43 |
| 导入服务 RSS / PSS（MiB） | 209.87 / 115.54 | 206.09 / 112.50 |
| 导入服务 / Root 扫描进程 FD | 127 / 96 | 127 / 96 |
| 采样主库 / WAL 峰值（MiB） | 97.55 / 0.97 | 97.59 / 3.27 |
| 终态主库 / WAL（MiB） | 93.53 / 0.50 | 93.53 / 0.50 |
| 大文件首页 / 末页（毫秒） | 29.09 / 13.80 | 42.99 / 11.96 |

WAL 的实测采样峰值增长约 2.3 MiB，终态大小不变。导入服务 CPU 秒下降，采样窗口也更短，因此不能直接推算全设备 CPU 占用率。两次采样组的单进程内存有波动，FD 峰值相同；Root 组首页请求中位数多 14 ms，但样本少，且无采样普通组未复现该方向，留待更大样本复核。

## 索引与布局

本轮只移除一个候选索引做独立库对照。保留正式库的 11 个节点和聚合二级索引；会话、问题及 diff 缓存的索引不属于这 11 个。

| 索引 | 用途 |
| --- | --- |
| `node_path` | 维护原始路径唯一性，支持子树路径范围和快照路径对比 |
| `node_identity` | 按设备及 inode 分组去重，同组内使用原始路径选 owner |
| `node_parent` | 节点表的父子顺序索引；目前的常用子项查询从 `aggregates` 取结果，作为候选评估 |
| `aggregate_parent`、`aggregate_incomplete`、`aggregate_depth` | 按父项求和、检测不完整子项及按深度自底向上汇总 |
| `children_logical`、`children_allocated`、`children_name` | 目录子项按逻辑空间、分配空间、名称分页 |
| `large_logical`、`large_allocated` | 全量大文件榜按逻辑空间或分配空间分页 |

小样本的 `EXPLAIN QUERY PLAN` 在两种库上给出相同的查询计划：快照路径、身份分组、深度、不完整子项及五类排序分别命中对应索引；详情按主键读取。简化父项求和在这个样本上只按 `sid` 用主键过滤。被移除的 `node_parent` 不在这些计划中，但这组结果不证明其它查询形态或更大的库也无差异。

暂缓改成整数会话键、压缩路径或使用 staging 表。它们会影响路径范围查询、增长对比与旧快照迁移；本轮没有这些布局方案的对照结果。若需回退，可将 `ImportPolicy.DEFAULT` 设回 256 动作、逐进度提交、原绑定方式，已保存的库无需迁移。

## 正确性检查

通过 Debug 构建、Android Lint、4 个 JVM 协议测试。真机 Profile 共报告 32 项，29 项通过，3 项未启用（额外 Root fixture、实时 `/data/data` 与旧规模入口）。覆盖普通和 Root 入库、硬链接 owner、Partial、原始字节路径、快照保留和删除、增长对比、旧 schema 迁移、跨线程导入可见性与分页 revision。取消、扫描中读取和杀死导入服务后恢复均通过。单次 10,101 节点生命周期用例的扫描中目录查询为 33.3 ms，取消请求至观察到终态为 41.5 ms；单次观察不代表性能分布，也不测量所有资源释放的时间。

最终构建的 10,001 节点 A/B/C/Replay 冒烟全部通过；C 和 Replay 都报告默认策略 `4096-eager-list`，资源采样 TSV 列完整。测试后恢复了原主 APK 和测试 APK，并核对了两者的 SHA-256。

原始结果在 `.local/scan-performance/step4-replay-100k/`、`step4-full-100k/`、`step4-root-resources-100k/`，包括逐次 JSON、温度、应用及测试包哈希、native build ID、原始采样；查询计划及回归日志在 `step4-full-100k/`。回放和普通 C 对照的主 APK SHA-256 为 `41455788BD9B26476925216220E227645A9B0D58326D99C96517C6BF1DED9332`；切换默认后，Root 采样与设备回归的主 APK 为 `59655AB3A08EB47B23ECF774E2FE0B006AC8D5FF3BE4C1CEDF8A6010BE2372CD`。同一批比较使用同一个主 APK。

本轮是同一台设备上对事务策略的对照，不能据此预测真实 `/data/data` 的耗时或与 NTFS 的差距。百万规模、近上限的资源占用和真实目录的分布差异留给整体验收；最终处理仍主要花在去重和目录汇总上，对应步骤 5。
