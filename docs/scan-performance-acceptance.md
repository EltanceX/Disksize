# 扫描性能：步骤 7 整体验收

2026 年 11 月 18 日。普通内部 F2FS 的 100,001 节点完整扫描中位数从 16.705 秒降至 6.635 秒（−60.3%），1,000,001 节点从 120.029 秒降至 57.822 秒（−51.8%）。10 万节点 Root 独立采样组从 16.361 秒降至 6.339 秒（−61.3%）。每组对照的条目、容量和完整性一致。

## 对照口径

在 Xiaomi sheng（Android 16、arm64、8 个在线 CPU、Linux 5.15.178）上，用同一个 Profile APK 在同一棵固定树上切换策略。构建审计匹配 arm64-v8a 和 x86_64 的 APK 内库与未剥离库的 build ID，核验扫描代码的有效参数为 `-O2 -g -DNDEBUG`。真机执行的是 arm64。报告版本 v1、SQLite schema 4、流协议 v4。SQLite 使用 WAL、`temp_store=FILE` 和 `cache_size=-8192`。

| 模式 | 对照 | 当前默认 |
| --- | --- | --- |
| A/B | 分开查询元数据及挂载，逐帧分配 | 合并查询并复用缓冲；A 不走传输 |
| C / Interaction | `256-eager-list`，旧最终处理，旧流水线 | `4096-eager-list`，优化后的最终处理和流水线 |
| Replay | `256-eager-list`，旧最终处理 | `4096-eager-list`，优化后的最终处理 |

对照是当前构建中的旧策略组合。[步骤 3 的旧 APK](./scan-performance-baseline.md)不参与计算加速比。每个测试组预热一轮、轮换两种策略的先后顺序，每次以新进程和新基准库运行，未清系统文件缓存。固定文件树的实际扫描包含根节点，因此传入 `-Size 100000` 时为 100,001 个节点：1,001 个目录和 99,000 个空文件。百万组有 1,001 个目录和 999,000 个空文件。建树、清理、Binder 建连和 Root 就绪单独计时。

## 扫描和回放

数值为中位数［最小值，最大值］，单位为秒。资源采样组单列；C 计到 journal 持久化并发布终态，不含客户端轮询、查询及页面绘制。A 是纯遍历，B 包含 pipe 和解码，Replay 从开库计到最终提交和预览。

普通内部 10 万 C 的 SQLite 导入中位数从 10.348 秒降至 5.590 秒，事务数从 429 次降至 41 次；去重、初始化和目录汇总的合计中位数从 5.049 秒降至 0.390 秒。候选的流水线仍花 6.206 秒，其中发送方等待 pipe 可写约 5.946 秒。导入与发送并行，这些时间不能相加。普通 B 的测试进程 CPU 从 1.157 降到 1.014 秒。

普通/Root 内部 10 万组每次都以 0 个问题、0 逻辑字节、4,136,960 分配字节完成；遍历同时打开的 FD 峰值为 2，结束归零。Root 组 producer UID 为 0、服务和 SQLite consumer 为普通 UID 10386。

外部样本使用相同配方，每个视图组内复用同一棵树。两组分别确认 FUSE (`0x65735546`) 和直达 F2FS (`0xF2F52010`)，正式结果均完整、无问题、容量一致。直达组扫描进程为 UID 0，SQLite 仍由普通 UID 10386 的独立服务持有。两组之间同时变化了视图和后端，不用这些数据单独量化 FUSE 开销。

百万正式组全部以 0 个问题、0 逻辑字节、41,562,112 分配字节完成，扫描 FD 在结束时归零。最终处理三项合计中位数从 62.026 降至 7.802 秒，事务数从 4,040 降至 327 次。候选流水线 50.029 秒，其中 SQLite 导入累计耗时 46.602 秒，仍是主要瓶颈。

两组 Replay 的逐行摘要在两种策略间一致，覆盖归属、容量、完整性和问题记录。硬链接样本仍为预期的 `partial`，报告 5,824 个问题；深宽目录样本完整。

## 取消与增长对比

普通内部 100,001 节点，三次正式配对。导入到约 5,000 节点时查询目录，然后发出取消请求并轮询终态。接着采集两份完整快照，其中一个文件新增 1 字节；对比验证文件、其父目录、总增量和缓存首页，较旧快照仍保留。所有对照均未为取消的扫描发布可用快照。

| 指标（ms） | 对照 | 当前默认 |
| --- | ---: | ---: |
| 导入中目录请求 | 18.7 [17.5, 22.8] | 29.9 [9.5, 38.8] |
| 取消到客户端观察到终态 | 76.4 [74.1, 76.7] | 65.8 [65.4, 66.1] |

对照的三个正式目录请求均返回 `stale-cursor`，候选的三个都返回有效的临时页面，因此这一行不做同类查询延迟的比较。两组对比均用 196 次同步请求，不含主动等待、Flutter 绘制或两次采集扫描；耗时范围重叠。

先前的交互批次在连续启动第二次快照扫描时捕获到系统 `dataSync` 前台服务超时，新扫描尚未导入节点。正式复测在两次不计时的采集前让应用重新进入前台，未改生产服务或系统设置；不将本次通过解读为已修复快速重启的系统超时。

## 构建与范围

双 ABI 的 Profile/Debug APK 和测试包构建成功；Android Lint、4 项 JVM 协议测试、`flutter analyze` 和 65 项 Flutter 测试通过。真机原生扫描、Root pipe、流式扫描合计 21 项全通过。真机索引、快照和设备测试通过 33 项，另有 3 项未启用（旧 Root 基线、旧规模测试入口、真实应用数据）。回归覆盖 v4 畸形帧、旧 schema 快照、稳定分页、取消、服务进程死亡、Root 扫描进程死亡及重新连接。中断会话保持临时状态且不生成可用快照。原主 APK 和测试 APK 均恢复并核对了设备上的 SHA-256。

上述重复对照均来自同一台 arm64 设备与受控样本，真实 `/data/data` 仅另测一次；这些结果不代表 x86_64、其他 Android 系统或 200 万节点上限。测试从应用前台开始，不覆盖锁屏或退到后台后的长时间扫描。

## 采纳与回退

保留现有默认：4,096 动作事务、优化的最终处理、合并元数据查询和 v4 缓冲复用；导入仍占主要时间，不引入遍历并发。保留原有读权限、扫描边界和协议校验，不需要修改 schema 或迁移快照。后续优先定位大文件首页的小幅退化，并单独复现快速重启前台服务的系统超时。

可用 `-CompareOverall` 复现全组合，或用三个单项开关定位单独策略。正式构建回退分别见[导入](./scan-performance-import.md)、[最终处理](./scan-performance-finalize.md)和[native](./scan-performance-native.md)报告；基准开关不是正式 APK 的运行时功能。

## 复现

用[扫描性能基准工具](../tools/scan-performance/README.md)覆盖安装并自动恢复开发包。串行执行设备任务；同一批的两种策略不换 APK。

```powershell
. ./.local/android-env.ps1
$run = @{ Serial = '<device-id>'; Suite = 'Custom'; CompareOverall = $true; RootInstall = $true; Warmups = 1 }
./tools/scan-performance/verify.ps1 @run -Size 100000 -Mode A,B,C -Repeats 3
./tools/scan-performance/verify.ps1 @run -Size 100000 -Mode C -Backend root -Repeats 3 -SampleResources
./tools/scan-performance/verify.ps1 @run -Size 100000 -Mode Interaction -Repeats 3
./tools/scan-performance/verify.ps1 @run -Size 100000 -Mode Replay -ReplayFixture dense-links -Repeats 2
./tools/scan-performance/verify.ps1 @run -Size 10000 -Mode Replay -ReplayFixture deep-wide -Repeats 2
./tools/scan-performance/verify.ps1 @run -Size 100000 -Mode C -View fuse -Repeats 2
./tools/scan-performance/verify.ps1 @run -Size 100000 -Mode C -View emulated-direct -Backend root -Repeats 2
./tools/scan-performance/verify.ps1 @run -Size 1000000 -Mode C -Repeats 3
```

首次百万组在第二个正式对照轮触发 30 分钟的设备端等待超时；日志没有保留超时前的状态，原因未能确定。该批成功的一对正式结果（116.538 和 58.913 秒）单独保留，不能代表三个重复，也不与重跑混算。第二次运行只留下两次预热，不计入统计。原 fixture 按归属标记清理，原 APK 恢复并核对哈希。新测试对固定树使用 10 分钟的终态等待上限，超时报告最后观察到的状态和节点数。
